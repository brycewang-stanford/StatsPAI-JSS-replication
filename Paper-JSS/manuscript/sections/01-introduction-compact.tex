\section{Introduction}\label{sec:intro}

Applied causal work now runs on a large and fragmented software stack. It
combines \proglang{Stata} commands, methodological-reference \proglang{R}
packages, and a growing but incomplete \proglang{Python} ecosystem.
A single project can require OLS and IV, staggered
difference-in-differences, regression discontinuity, synthetic control,
matching, double machine learning, sensitivity analysis, and publication
tables. The statistical literature has converged toward more explicit
design checks and estimator-specific inference
\citep{imbens2009recent,angrist2009mostly,callaway2021difference,
roth2023whats,wing2024designing,baker2026difference,rambachan2023more,abadie2010synthetic,
chernozhukov2018double}. The software interface has not followed. Users
still cross package boundaries, result classes, naming conventions, and
diagnostic vocabularies. Large-language-model agents add a further
constraint, because they need typed schemas and structured errors, not
prose-only help pages.

This paper introduces \statspai{}, a \proglang{Python} platform for
applied econometrics and causal inference. The package provides
(i) a unified \code{import statspai as sp} surface across common causal
designs, (ii) shared reporting conventions for mature estimator results,
diagnostics, citations, and export methods, (iii) a machine-readable registry that can be exposed through a
Model Context Protocol (MCP) server~\citep{anthropic2024mcp}, and (iv) an explicit validation
discipline against analytical targets, canonical \proglang{R}
implementations, and selected \proglang{Stata} migration bridges. This
article describes \statspai{} \StatsPAIVersion{}, distributed on PyPI
(\code{pip install statspai==\StatsPAIVersion{}}) under the MIT licence.
The source is tag \code{v\StatsPAIVersion{}} of
\url{https://github.com/brycewang-stanford/StatsPAI}. Every \statspai{}
number in the article was produced by that release, against the pinned
reference environments of Section~\ref{sec:compdetails}.

A short paper on the package appeared in the \emph{Journal of Open
Source Software}~\citep{wang2026statspaijoss}. It established the
unified interface, the registry and agent schemas, the structured result
objects, and the existence of a same-byte cross-language parity harness
and of a 1{,}000-replication coverage run for OLS, DiD, and IV. This
article does not re-establish those facts. Its question is the one a
parity harness raises but cannot answer by itself: \emph{what exactly
does a validation label certify?} A green parity row can mislead in four
ways. It can be earned by the wrong code, such as a \proglang{Python}
wrapper that calls the \proglang{R} reference it is compared against. It
can vouch for the wrong function, as when an alias is credited with
evidence that ran another entry point. It can rest on the wrong
statistical comparison, judging a stochastic estimator against its
sampling standard error instead of its own Monte Carlo error. Or it can
describe a configuration or an output the user is not relying on, as
when a parity row for a coefficient is cited as evidence for its
standard error.

The contribution is a design that makes these failure modes checkable,
applied to the package's own validated core. A label reaches a user
through four links, and each one is verified, not merely asserted
(Figure~\ref{fig:evidence-chain}). The first is the \emph{implementation}
a parity row exercised, established by a call trace bound to the source
files on that path (Section~\ref{sec:track-a}). The second is the
\emph{entry point}, because an inherited label must name a test that ran
the inheriting function (Section~\ref{sec:attachment-audit}). The third is
the \emph{configuration and output}. For a fitted object of the
twelve-estimator core, \code{sp.validation\_scope} reports which artifacts
ran its variant, inference option, and code path, and which outputs they
compared (point estimate, standard error, interval coverage, or
diagnostic; Section~\ref{sec:validation-tiers}). The fourth is
\emph{applicability}. Automated diagnostics report a check that does not
exist for a fit as not applicable, not as missing
(Section~\ref{sec:ex-card}).

The design is not a proposal tried on an example. It is implemented
inside \statspai{}, its labels are returned by the same calls that fit
the models, and each link above is held by a test in the package's own
suite. It carries over to any package that publishes evidence tiers.

Around these links, the article fixes an adjudication procedure for
disagreements (Section~\ref{sec:adjudication}) and reserves the
stochastic grade T3 for seed-replicated equivalence against a stated
margin. Applying the design to the package found defects that numerical
parity alone had missed. Two Honest-DiD rows compared \proglang{R} with
itself, an IV entry point silently ignored a requested small-sample
cluster covariance, and the clustered standard errors of a fixed-effects
default over-covered (0.979 at nominal 0.95). Section~\ref{sec:parity}
reports these and the others.

The registry distinguishes \code{certified}, \code{validated},
\code{api\_stable}, and \code{experimental} symbols, and the tier is
queryable at call time. Numerical validation is therefore an evidence
tier rather than a blanket claim over the whole API surface, and the full census
opens Section~\ref{sec:parity}.

Listing~\ref{lst:motivating} fixes ideas. It estimates the classical
\citet{card1995using} returns-to-schooling design four ways from a single
import: OLS, instrumental variables, double machine learning
\citep{chernozhukov2018double}, and a causal forest
\citep{wager2018estimation}. Three of the four fitted objects belong to
three different result classes, and one call renders them into a single
publication table. Three design properties recur throughout the paper.
The estimator surface is \emph{flat}, with classical and modern methods
as siblings under \code{sp.}. The result objects are
\emph{interoperable}, so mixed estimators feed directly into one
\code{sp.regtable} call. And the platform exposes \emph{audit hooks}
(\code{sp.audit}) that list the diagnostic evidence a design demands but
the user has not yet supplied. Section~\ref{sec:ex-card} runs the same
session at a prompt and prints what each of these calls returns.
Section~\ref{sec:ex-csdid} measures what the shared result contract buys
on a harder case. There, the natural hand-composed shortcut of
rebuilding an event-study covariance from reported standard errors
overstates a Honest-DiD breakdown value by 26\%.

Every listing in this paper is executed verbatim by the replication
archive's listing audit. Each printed transcript is also replayed
statement by statement and compared line for line with the output the
code produces (Section~\ref{sec:reproducibility}).

\begin{lstlisting}[caption={\statspai{} reproduces and extends Card
(1995) from a single import; classical and modern estimators are
siblings under \code{sp.} and return one interoperable result
contract.},label={lst:motivating},captionpos=b]
import statspai as sp

card = sp.datasets.card_1995()
X    = ["exper", "expersq", "black", "south", "smsa"]

ols = sp.regress("lwage ~ educ + " + " + ".join(X), data=card)
iv  = sp.iv("lwage ~ " + " + ".join(X) + " + (educ ~ nearc4)",
            data=card)
dml = sp.dml(card, y="lwage", d="educ", X=X,
             model="plr", n_folds=5, random_state=42)
cf  = sp.causal_forest("lwage ~ educ | " + " + ".join(X), data=card,
                       n_estimators=2000, discrete_treatment=False,
                       random_state=42)

table = sp.regtable(ols, iv, dml, keep=["educ", "theta"], stars=True,
                    model_labels=["OLS", "2SLS", "DML PLR"])
table.to_docx("returns_to_schooling.docx")
\end{lstlisting}

The package surface is deliberately broad. It spans classical regression
and panel models, the modern DiD, RD, and synthetic-control literatures,
ML-based treatment-effect estimation, matching and weighting,
sensitivity analysis, and publication output. Breadth is not the paper's
evidentiary claim. In this paper, \emph{validation evidence} means that a
specific artifact exists. That artifact is known-truth recovery,
cross-language parity on identical data bytes, Monte Carlo coverage, or
an explicit convention disclosure. Only the first two earn the
\code{validated} and \code{certified} registry labels
(Section~\ref{sec:parity}). Coverage rows and disclosures are recorded
but earn nothing on their own. Unit and regression tests are
API-contract evidence, and an \code{api\_stable} helper has a stable call
signature. Neither acquires statistical credibility by sitting next to
validated estimators. The validated claim is limited to the
twelve-estimator core of Section~\ref{sec:decathlon} and to the named
rows of the parity ledger.

The closest implementations cover important parts of this terrain, but
with different centers of gravity. Table~\ref{tab:related-software}
states the comparison directly. Empirical comparisons appear later, in
the same-byte parity rows
(Tables~\ref{tab:track-a-cross-language-snapshot}
and \ref{tab:headline-parity}) and in the timing study
(Figure~\ref{fig:track-c-loglog}). Per-entry-point detail is generated
into \path{Paper-JSS/parity/replacement-table.md}. The contribution is
therefore an integration-and-validation layer around reference software.
It is not a claim that \statspai{} supersedes specialized packages or
reference implementations in their home domains, such as
\pkg{fixest}, \pkg{did}, \pkg{rdrobust}, \pkg{Synth},
\pkg{synthdid}, \pkg{DoubleML}, or \pkg{grf}. Representative software
citations include \pkg{Synth}, \pkg{MatchIt}, \pkg{DoubleML},
\pkg{EconML}, \pkg{CausalML}, and \pkg{DoWhy}
\citep{abadie2011synth,ho2011matchit,bach2022doubleml,econml,
chen2020causalml,sharma2020dowhy}.

The replication archive carries the executable ledgers that decide
whether a label is justified, and an evidence map that routes each
validation-scope, reproduction, and release-boundary question to the
artifact that answers it.

Section~\ref{sec:examples} runs seven worked examples, with staggered
DiD as the main case study. Sections~\ref{sec:parity}--\ref{sec:agentbench}
report the validation, performance, and interface evidence, and

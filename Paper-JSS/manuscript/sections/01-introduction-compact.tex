\section{Introduction}\label{sec:intro}

Statistical packages increasingly publish evidence labels: this function
is ``validated'', that one ``experimental''. Such a label is useful only
if a user can find out what stands behind it for the fit in front of
them. Did the comparison run this variant? Did it compare the standard
error, or only the coefficient? Did the code that was compared run in
this package at all? This article describes \statspai{}, a
\proglang{Python} package for applied econometrics and causal inference,
and a design that lets those questions be answered from the running
software. Given a fitted object, \code{sp.validation\_scope} reports
which reference runs covered its variant and inference option and which
outputs they compared. It reports ``not covered'' when none did.

Numerical checking of statistical software has a long record.
\citet{mccullough1999numerical} warned that users cannot safely assume
their software is accurate and called for benchmarks of specialized
econometric procedures. The NIST Statistical Reference Datasets
\citep{filliben1999strd} supply data with certified values for general
procedures, and the R Validation Hub \citep{nicholls2020riskbased} judges
the risk of a package from its purpose, maintenance, usage, and testing.
\proglang{Stata} is certified before each release by an automated suite of
scripts that compare results with stored ones \citep{gould2001statistical},
and rOpenSci reviews statistical packages against published standards
\citep{padgham2021statistical}.
Those traditions judge a procedure or a package as a whole. A label in a
package with many estimators, inference options, and thin wrappers can be
wrong in a different way, while every number in its test suite stays
correct.

A green parity row, meaning one comparison of \statspai{} with a
reference program on identical data, can mislead in four ways. It can be
earned by the wrong code, such as a \proglang{Python} wrapper that calls
the \proglang{R} reference it is compared against. It can vouch for the
wrong function, as when an alias is credited with evidence that ran
another entry point. It can rest on the wrong statistical comparison,
judging a stochastic estimator against its sampling standard error
instead of its own Monte Carlo error. Or it can describe a configuration
or an output the user is not relying on, as when a row for a coefficient
is cited as evidence for its standard error.

The contribution is a design that makes these failures checkable, and
its application to this package. A label reaches a user through four
links (Figure~\ref{fig:evidence-chain}). The first is the
\emph{implementation} a row exercised, established by a call trace bound
to the source files on that path (Section~\ref{sec:track-a}). The second
is the \emph{entry point}, because an inherited label must name a test
that ran the inheriting function (Section~\ref{sec:attachment-audit}).
The third is the \emph{configuration and output}
(Section~\ref{sec:validation-tiers}). The fourth is
\emph{applicability}: automated diagnostics report a check that does not
exist for a fit as not applicable, not as missing
(Section~\ref{sec:ex-card}). Each link is held by a test in the package's
own suite.

The reach of these checks narrows as the claim gets stronger, and the
reader should see that first. The registry labels
\RegistryCertified{} symbols \code{certified} and \RegistryValidated{}
\code{validated}. The call trace covers the \RParityModuleCount{} modules
of the parity study, which back \ParityTrackACrossCount{} of those
symbols. The configuration-level query covers 40 entry points, among them the twelve suite estimators. For the
rest of the registry, a label names its evidence file but says nothing
finer. The labels are assigned by the package's own harness and have not been
audited externally, and they describe what was run, not whether a method
suits a design.

Applying the design found defects that numerical parity alone had
missed. Two Honest-DiD rows compared \proglang{R} with itself, an
instrumental-variables (IV) entry point silently ignored a requested
small-sample cluster covariance, and the clustered standard errors of a
fixed-effects default over-covered (0.979 at nominal 0.95).
Section~\ref{sec:parity} reports these and the others, along with
results that remain unfavourable.

The package itself is an integration layer for a stack that is otherwise
fragmented across \proglang{Stata} \citep{statacorp2023stata},
\proglang{R} \citep{rcoreteam2025r}, and \proglang{Python}
\citep{vanrossum2009python}. A single project can require ordinary least
squares (OLS), IV, staggered difference-in-differences (DiD), regression
discontinuity (RD), synthetic control, matching, double machine learning
(DML), sensitivity analysis, and publication tables, and the literature
now expects design-specific checks for each
\citep{imbens2009recent,angrist2009mostly,roth2023whats,wing2024designing,baker2026difference}.
\statspai{} offers one import, shared reporting for its mature results, a
machine-readable registry that also serves large-language-model (LLM)
agents through a Model Context Protocol (MCP) server
\citep{mcp2026specification}, and a stated validation discipline. It does
not supersede the specialized packages it is compared against.

A short paper on the package appeared in the \emph{Journal of Open
Source Software}~\citep{wang2026statspaijoss}. It established the
unified interface, the registry and agent schemas, and the existence of
a same-data parity harness and of a 1{,}000-replication coverage run.
That paper's facts are not re-established here. This article describes \statspai{} \StatsPAIVersion{}, available from PyPI
(\code{pip install statspai==\StatsPAIVersion{}}) under the MIT licence,
tag \code{v\StatsPAIVersion{}} of
\url{https://github.com/brycewang-stanford/StatsPAI}. Its numbers are
those of that release, against the pinned reference environments of
Section~\ref{sec:compdetails}. Later releases change some defaults, and
\code{MIGRATION.md} lists each change.

Listing~\ref{lst:motivating} fixes ideas. It fits the
\citet{card1995using} returns-to-schooling data with OLS, IV, DML
\citep{chernozhukov2018double}, and a causal forest
\citep{wager2018estimation} from one import. These are four different
analyses of the data, not four estimates of one parameter
(Section~\ref{sec:ex-card}). The first three objects render into one
table. Section~\ref{sec:ex-card} continues the session and prints what
the calls return. Every listing in this paper is executed verbatim by
the replication archive, and each printed transcript is compared line
for line with the output the code produces
(Section~\ref{sec:reproducibility}).

\begin{lstlisting}[caption={Four analyses of the \citet{card1995using}
data from a single import, and one table of the three that report a
coefficient.},label={lst:motivating},captionpos=b]
import statspai as sp

card = sp.datasets.card_1995()
X = ["exper", "expersq", "black", "south", "smsa"]

ols = sp.regress("lwage ~ educ + " + " + ".join(X), data = card)
iv = sp.iv("lwage ~ " + " + ".join(X) + " + (educ ~ nearc4)",
           data = card)
dml = sp.dml(card, y = "lwage", treat = "educ", covariates = X,
             model = "plr", n_folds = 5, random_state = 42)
cf = sp.causal_forest("lwage ~ educ | " + " + ".join(X), data = card,
                      n_estimators = 2000, discrete_treatment = False,
                      random_state = 42)

table = sp.regtable(ols, iv, dml, keep = ["educ", "theta"], stars = True,
                    model_labels = ["OLS", "2SLS", "DML PLR"])
table.to_docx("returns_to_schooling.docx")
\end{lstlisting}

In this paper, \emph{validation evidence} means that a specific artifact
exists: known-truth recovery, parity with a reference program on identical
data, Monte Carlo coverage, or an explicit disclosure of a convention. An
\code{api\_stable} helper has a stable call signature and no statistical
grade.

Table~\ref{tab:related-software} sets \statspai{} beside the closest
implementations, among them \pkg{pyfixest} \citep{pyfixest2025pyfixest},
\pkg{EconML} \citep{econml}, \pkg{CausalML} \citep{chen2020causalml}, and
\pkg{DoWhy} \citep{sharma2020dowhy}. The specialized packages go deeper in their home
domains, and a user who needs one family, or an option a reference has
and \statspai{} lacks, should use the reference. Prefer \pkg{DoubleML} or \pkg{EconML} for DML model classes beyond PLR, IRM,
PLIV, and IIVM, such as sample selection or quantile targets, \pkg{CausalML} for
uplift modelling, \pkg{DoWhy} for graphical causal models and root-cause
analysis, \pkg{linearmodels} for asset-pricing models, and \pkg{fixest} for its
formula syntax and option depth. \pkg{diff-diff} \citep{gerber2026diffdiff}
covers modern DiD, RD, synthetic control, and Honest-DiD, ships a guide for LLM
agents, and implements the efficient DiD estimator of \citet{chen2025efficient},
which \statspai{} does not for general designs; prefer it there.
\pkg{CausalPy} \citep{pymclabs2026causalpy} takes a largely Bayesian route to
quasi-experimental designs. Result-unifying layers such as \pkg{broom}
\citep{robinson2026broom}, \pkg{modelsummary}
\citep{arelbundock2022modelsummary}, and \pkg{marginaleffects}
\citep{arelbundock2024marginaleffects} offer one reporting surface over
many \proglang{R} model classes; they do not carry evidence labels and do
not supply estimators. The advantage of \statspai{} is a single contract
and evidence ledger across families. The price is a larger dependency surface (15 core
requirements), a young code base with a long correction history
(Appendix~\ref{app:corrections}), and a lag behind upstream options.
